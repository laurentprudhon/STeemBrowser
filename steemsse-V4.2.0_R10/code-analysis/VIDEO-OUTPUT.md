# Video Output Generation - Steem SSE

This document provides a detailed technical analysis of the video output pipeline in Steem SSE, tracing the chain of signals from the CPU and memory to the final display output.

## 1. Video Signal Generation: Timing and Synchronization

The video signal is not generated by a single component but is a coordinated effort between the **Glue chip** and the **Shifter chip**.

### Timing Control (The Glue Chip)
The **Glue chip** (`steemsse-V4.2.0_R10/steem/headers/glue.h`) acts as the master clock and timing controller for the video system. It defines the structure of the video frame and the individual scanlines.

- **Pixel Clock**: The system operates on a 32 MHz pixel clock.
- **Scanline Structure**: Each scanline is divided into regions:
    - **HBL (Horizontal Blanking)**: Periods where no visible data is output.
    - **HSYNC**: The horizontal synchronization signal.
    - **DE (Display Enable)**: The window during which the Shifter is active and outputting visible pixels.
- **Vertical Synchronization**: The Glue chip tracks the current scanline index (`TGlue::VCount`) and generates the **VSYNC** signal when the frame is complete (`TGlue::Vbl()`).

The main synchronization loop is driven by `TGlue::GetNextVideoEvent()`, which ensures that the emulator's timing remains cycle-accurate relative to the Atari ST hardware.

### Synchronization Chain
1. **Glue chip** determines if the current cycle falls within the **DE (Display Enable)** window.
2. If $\text{Cycle} \in \text{DE}$, the Glue chip triggers the **Shifter** to render the corresponding portion of the scanline.
3. The Glue chip manages borders and overscan effects through `TGlue::CheckSideOverscan()` and `TGlue::CheckVerticalOverscan()`.

## 2. The Shifter Chip and Memory Interaction

The **Shifter chip** (`steemsse-V4.2.0_R10/steem/shifter.cpp`) is responsible for converting raw memory data into color indices.

### Memory Access (DMA)
Unlike a standard DMA controller that might move blocks of memory, the Shifter performs **interleaved memory access**. It fetches data from RAM in synchronization with the pixel clock.

- **The Draw Pointer**: The Shifter maintains a `shifter_draw_pointer` (`steemsse-V4.2.0_R10/steem/shifter.cpp:65`), which is the absolute memory address of the video data to be rendered.
- **Interaction with MMU**: The Shifter relies on the **MMU** (`steemsse-V4.2.0_R10/steem/headers/mmu.h`) to translate logical video addresses into physical RAM locations. The MMU's `ReadVideoCounter()` provides the current address based on the pixel position.
- **Fetch Cycle**: As the Glue chip signals "Display Enable," the Shifter fetches bytes from memory. Depending on the resolution, one byte can represent multiple pixels (e.g., 16 pixels in low res).

## 3. CPU Configuration of Video Mode

The CPU configures the video system by writing to memory-mapped I/O registers.

### Resolution and Mode Control
The CPU sets the video resolution via the `ShiftMode` register. In Steem SSE, this is mirrored in `TGlue::ShiftMode` and `TShifter::ShiftMode`.
- **00**: Low Resolution
- **01**: Medium Resolution
- **10**: High Resolution
- **11**: STE Super Hi-Res

### Palette Configuration
The color palette is stored in a set of registers from `0xFF8240` to `0xFF825E`.
- The CPU writes a 9-bit (ST) or 12-bit (STE) color value to these addresses.
- `TShifter::SetPal()` (`steemsse-V4.2.0_R10/steem/shifter.cpp:813`) updates the internal `STpal` array, which is used during the rendering phase.

### Video Base Address
The starting point of the video data in RAM (`vbase`) is configured by the CPU, determining where the Shifter begins fetching data at the start of a frame.

## 4. Converting RAM to RGB Output

The process of turning a byte in RAM into a pixel on the screen follows these steps:

1. **Fetch**: The Shifter fetches a byte from RAM at the current `shifter_draw_pointer`.
2. **Decompression (Bit-Shifting)**: The Shifter "shifts" the bits of the byte to determine the color index for the current pixel. 
    - In **Low Res**, 4 bits represent one pixel (16 colors).
    - In **Med Res**, 2 bits represent one pixel (4 colors).
    - In **High Res**, 1 bit represents one pixel (2 colors).
3. **Palette Lookup**: The extracted bit-index is used to look up the actual color value in the `STpal` array.
4. **DAC Approximation**: The resulting color (e.g., a 9-bit value for ST) is converted into an RGB triplet:
    - **ST (9-bit)**: 3 bits per RGB component.
    - **STE (12-bit)**: 4 bits per RGB component.
5. **Output**: The rendered pixels are stored in a scanline buffer (`TShifter::Scanline`), which is then passed to the host's display system (`steemsse-V4.2.0_R10/steem/display.cpp`).

## 5. Impact of Video Modes

The chosen video mode fundamentally changes how memory is interpreted and how the Shifter behaves.

| Mode | Resolution | Colors | Planes | Bit-depth | Memory Layout |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Low** | $320 \times 200$ | 16 | 4 | 4 bits/px | 160 bytes/line |
| **Medium** | $640 \times 200$ | 4 | 2 | 2 bits/px | 160 bytes/line |
| **High** | $640 \times 400$ | 2 | 1 | 1 bit/px | 160 bytes/line |
| **STE** | Various | 512 | Variable | Variable | Variable |

### Technical Consequences of Modes:
- **Bandwidth**: High resolution requires more fetches per scanline but results in fewer colors.
- **Rendering Complexity**: In `steemsse-V4.2.0_R10/steem/shifter.cpp`, the `RenderVisibleScanline()` function branches into different rendering paths (`RenderLowResScanline`, `RenderMedResScanline`, etc.) to handle these differing bit-depths.
- **STE Enhancements**: The STE modes introduce a larger palette (up to 512 colors) and support for hardware horizontal scrolling, achieved by offsetting the `shifter_draw_pointer` and applying a bit-shift to the fetched data.
